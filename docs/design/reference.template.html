1. Status and use

Draft for review. This is not an approved Drupal standard. It is an AI-assisted reference prepared for Mike Gifford’s Drupal Core Lab. It proposes reviewer contracts; it does not certify accessibility or prescribe a completed Default Admin design system.

This document uses the Claro guide as an organisational reference, not as a source of current Default Admin token values. It adds semantics, ownership, request-theme context, preferences, printing and third-party editor boundaries.

Read each kind of evidence differently
LabelMeaning
Published guidanceA linked source describes an existing standard or recommendation. Its scope and version still matter.
Observed behaviourA specific capture shows what rendered. It can include defects, test-data effects or collector limitations.
Proposed reviewer ruleA stable rule ID describes what we want a reviewer to examine. All rules in this draft remain unapproved.
Open questionThe intention, owner, implementation or evidence remains unresolved. Do not fill gaps with a majority-style guess.

When sources conflict, identify the conflict. Preserve HTML meaning and applicable accessibility requirements; verify Drupal guidance against the target version. A common pattern is evidence of repetition, not proof of correctness. No proposal here should become a blocking CI rule before its scope, exceptions and fixtures have been reviewed.

2. Theme and request context

A route is not a theme. Drupal can select the active theme for a request through theme negotiators. Record that selection separately from the configured default theme, configured admin theme and any theme names found in stylesheet paths.

The Lab should show an observed theme change immediately and retain a transition history. A missing hint means unknown, even where Default Admin assets are present. Additional theme negotiation for language, region or topic must remain visible in the comparison context.

4. Foundations: typography, spacing and surfaces

Define component roles before freezing numbers. A page title, field label, table header and editor-content heading have different jobs. Reuse the target theme’s existing typography and spacing system, then document any additional variants. The current evidence is not a complete token extraction.

5. Semantics: bold, italics and hierarchy

Ask what the text means, then how its component is styled. A heavier label can remain a label. A heading should retain its heading element. Italics alone do not establish stress emphasis. The reference examples below illustrate decisions, not exact Default Admin visuals.

Meaning and presentation are separate decisions
IntentMarkup or styling decision
Name a form controlKeep a label and its control association; use the component’s label style.
Identify a sectionUse an appropriate heading level and the heading component.
Express importance or urgencyUse strong where that meaning is intended.
Express stress emphasisUse em where emphasis changes the reading.
Change a component’s visual hierarchyUse a scoped component variant; do not manufacture semantic importance.

6. Colour roles and relationships

Palette selection should answer: what is the surface, what is placed on it, what state is conveyed, and what other cue survives when colour changes? A swatch can have several valid uses; a passing pair does not establish the correct semantic use.

Illustrative role groups; these are not Drupal CSS token names
Role groupPair or relationshipReview question
Surface and contentsurface.default ↔ text.default / text.secondaryIs each text role readable on every surface where it appears?
Actionsaction.primary.background ↔ action.primary.foregroundDoes the pair convey task priority and preserve readable interaction states?
Boundariescontrol.boundary ↔ adjacent surfacesCan the user identify the necessary control edge?
Statusstatus.error / warning / success / informationWhat text, icon or structural cue carries the meaning without colour?
Interactionfocus / selected / hover / invalid / disabledCan overlapping states be distinguished without one masking another?

Store valid pairings and exceptions with the component contract. Do not assume that red always means error or that blue always means a link. Enhanced contrast targets such as 7:1 need a separately declared scope; they are not silently substituted for the WCAG AA text thresholds.

A contrast-mode name is not a contrast measurement. Native OS testing is distinct from browser emulation. The initial-load scans do not verify keyboard focus, error creation, task feedback or script-driven animation.

9. Print is a first-class output

Define print intent for each page family. A content list, a configuration record, an article draft and a help page may preserve different context. Removing interactive chrome can be reasonable, but blanket selectors can also remove meaningful content.

Use scoped print CSS and review the resulting document. Reset persistent positioning where it conflicts with paper flow, preserve useful table headers, and keep headings with their content. These are proposed implementation directions, not a tested patch for Drupal.

Known collector gap: the current overlap heuristic measures the 1280px emulated print viewport. It reported zero intersections while paper-width PDFs visibly showed overlap. Treat those zeroes as inconclusive. Validate paper-size geometry and fragmentation before using the heuristic as a rule gate.

10. CKEditor and authored content

CKEditor has both interface styles and content styles. An editor toolbar need not look identical to a Drupal button, and an authored heading need not look like an administrative page title. Overrides should follow a recorded intent and remain scoped to the correct region.

The current Article capture contains 101 editor UI elements and three editable-content elements on each side. That establishes initial editor presence only. Add a known test node with text, headings, emphasis, links, lists and a table before testing edit/save/frontend consistency. Record its text format and the actual frontend theme. Use test content; never collect credentials or private production material.

11. Other themes, languages and recipes

Extend this reference through theme-specific profiles. Keep shared semantic expectations separate from typography, colour and layout choices. A recipe can change the available content types, fields and editor configuration without a theme change. Track those changes rather than treating the old fixture as universal.

13. Rules for AI reviewers and maintainers

  1. Read this document’s status and the target version before evaluating a page.
  2. Identify component, owner, theme and state. Preserve unknown values.
  3. Use a stable rule ID and cite its source or evidence. Separate observation from intended behaviour.
  4. Compare equivalent contexts. Do not turn a different theme, translated string or editor-content style into a defect merely because it differs.
  5. Report introduced, resolved, persistent and not-comparable findings separately. Do not subtract totals to infer matching findings.
  6. For bold or italics, explain the intended meaning and the component variant before suggesting markup or CSS changes.
  7. Propose the smallest change at the owning layer. Do not apply site-wide overrides to hide a component-level problem.
  8. Record evidence gaps and intentional exceptions. No automatic fix or conformance claim follows from this draft.

The canonical docs/design/contracts.json file generates the rule cards and embedded application/json block. Run node scripts/build-design-reference.mjs after editing it. It is a draft interchange format; the collector reads print-rule metadata for draft review candidates, not general enforcement. Point an AI at this HTML now; integrate machine enforcement only after the contracts are reviewed.
