1. Status and use

Draft for review. This is not an approved Drupal standard. It is an AI-assisted reference prepared for Mike Gifford’s Drupal Core Lab. It proposes reviewer contracts; it does not certify accessibility or prescribe a completed Default Admin design system.

This document uses the Claro guide as an organisational reference, not as a source of current Default Admin token values. It adds semantics, ownership, request-theme context, preferences, printing and third-party editor boundaries.

Read each kind of evidence differently
LabelMeaning
Published guidanceA linked source describes an existing standard or recommendation. Its scope and version still matter.
Observed behaviourA specific capture shows what rendered. It can include defects, test-data effects or collector limitations.
Proposed reviewer ruleA stable rule ID describes what we want a reviewer to examine. All rules in this draft remain unapproved.
Open questionThe intention, owner, implementation or evidence remains unresolved. Do not fill gaps with a majority-style guess.

When sources conflict, identify the conflict. Preserve HTML meaning and applicable accessibility requirements; verify Drupal guidance against the target version. A common pattern is evidence of repetition, not proof of correctness. No proposal here should become a blocking CI rule before its scope, exceptions and fixtures have been reviewed.

2. Theme and request context

A route is not a theme. Drupal can select the active theme for a request through theme negotiators. Record that selection separately from the configured default theme, configured admin theme and any theme names found in stylesheet paths.

The Lab should show an observed theme change immediately and retain a transition history. A missing hint means unknown, even where Default Admin assets are present. Additional theme negotiation for language, region or topic must remain visible in the comparison context.

CTX-01 Compare equivalent contexts

Proposed reviewer rule · not adopted

Compare a component only within a declared theme, account, language, direction, viewport, state and preference context. Preserve unknown theme evidence.

Applies to
All themes and regions
How to review
Record actual, configured and stylesheet evidence separately; show context transitions.
Exceptions and limits
Intentional theme or context changes are explained, not suppressed.
Basis
Drupal main: ThemeNegotiator · Evidence: crawl-20261017

4. Foundations: typography, spacing and surfaces

Define component roles before freezing numbers. A page title, field label, table header and editor-content heading have different jobs. Reuse the target theme’s existing typography and spacing system, then document any additional variants. The current evidence is not a complete token extraction.

Observed values, not proposed universal constants
Captured componentObserved valueInterpretation
Article page title29 CSS px; font weight 575Snapshot of this component at this viewport, not a heading-size mandate.
Visible Article labels14 CSS px; weights 525 and 400; normal font styleMultiple variants exist. Determine each label’s role before calling one inconsistent.
Article font stackBegins with Inter, followed by system fallbacksDo not infer the font that actually rendered from the computed stack alone.

These examples come from the 15:08 UTC capture on 17 October 2026. Breakpoints, font availability, translations and component variants can change the result. Surface hierarchy, icon sizing and spacing scales still need a source-level inventory at the pinned commit. This document deliberately does not invent a replacement palette, icon set or exact spacing scale.

TOK-01 Reuse roles, not copied values

Proposed reviewer rule · not adopted

Use the existing component and token system before introducing another spacing, type or colour value.

Applies to
Theme and component CSS
How to review
Trace a computed value to its token, library and selector before proposing an override.
Exceptions and limits
A deliberate component variant can justify a new token. Token names below are illustrative, not shipped CSS variables.
Basis
Proposed Lab contract; no external adoption claimed.

5. Semantics: bold, italics and hierarchy

Ask what the text means, then how its component is styled. A heavier label can remain a label. A heading should retain its heading element. Italics alone do not establish stress emphasis. The reference examples below illustrate decisions, not exact Default Admin visuals.

Meaning and presentation are separate decisions
IntentMarkup or styling decision
Name a form controlKeep a label and its control association; use the component’s label style.
Identify a sectionUse an appropriate heading level and the heading component.
Express importance or urgencyUse strong where that meaning is intended.
Express stress emphasisUse em where emphasis changes the reading.
Change a component’s visual hierarchyUse a scoped component variant; do not manufacture semantic importance.

SEM-01 Structure before appearance

Proposed reviewer rule · not adopted

Preserve headings, labels, legends and table relationships when restyling. Visual weight alone is not a structural role.

Applies to
Shared markup and all themes
How to review
Inspect structure and relationships alongside computed styling.
Exceptions and limits
A component redesign may change structure with explicit review.
Basis
Drupal user interface standards

SEM-02 Importance and emphasis

Proposed reviewer rule · not adopted

Use strong for importance or urgency, and em for stress emphasis. Choose meaning before its appearance.

Applies to
Interface text and authored content
How to review
Review the intended meaning; do not infer it from font weight or italics.
Exceptions and limits
Other HTML elements have distinct meanings; do not replace b or i indiscriminately.
Basis
HTML text-level semantics

SEM-03 Labels are components

Proposed reviewer rule · not adopted

Style labels through the label component. Do not add strong merely to obtain a heavier label.

Applies to
Form labels
How to review
Compare matching label variants; verify association with the control.
Exceptions and limits
Required, optional, checkbox and composite labels can have different documented variants.
Basis
Drupal form elements · Evidence: article-labels

SEM-04 References survive updates

Proposed reviewer rule · not adopted

Retain working, unambiguous naming, description and error references after AJAX updates.

Applies to
Interactive components
How to review
Resolve ordered ID references; distinguish generated-ID changes from broken relationships.
Exceptions and limits
Matching hashes do not establish identical full accessible names.
Basis
Proposed Lab contract; no external adoption claimed. · Evidence: crawl-20261017

6. Colour roles and relationships

Palette selection should answer: what is the surface, what is placed on it, what state is conveyed, and what other cue survives when colour changes? A swatch can have several valid uses; a passing pair does not establish the correct semantic use.

Illustrative role groups; these are not Drupal CSS token names
Role groupPair or relationshipReview question
Surface and contentsurface.default ↔ text.default / text.secondaryIs each text role readable on every surface where it appears?
Actionsaction.primary.background ↔ action.primary.foregroundDoes the pair convey task priority and preserve readable interaction states?
Boundariescontrol.boundary ↔ adjacent surfacesCan the user identify the necessary control edge?
Statusstatus.error / warning / success / informationWhat text, icon or structural cue carries the meaning without colour?
Interactionfocus / selected / hover / invalid / disabledCan overlapping states be distinguished without one masking another?

Store valid pairings and exceptions with the component contract. Do not assume that red always means error or that blue always means a link. Enhanced contrast targets such as 7:1 need a separately declared scope; they are not silently substituted for the WCAG AA text thresholds.

COL-01 Colour has an explicit purpose

Proposed reviewer rule · not adopted

Map foreground, surface, boundary and state roles together. Do not assign meaning from a palette swatch alone.

Applies to
All colour modes
How to review
Review actual rendered pairs, simultaneous states and a non-colour cue.
Exceptions and limits
Decorative colours need no state meaning. Existing colour-only failures are recorded rather than legitimized.
Basis
WCAG 2.2: use of colour

COL-02 Check actual contrast pairs

Proposed reviewer rule · not adopted · external requirement has its own source

Apply WCAG text contrast requirements to actual foreground/background pairs, including their exceptions.

Applies to
Rendered text
How to review
Use 4.5:1 for ordinary text and 3:1 for qualifying large text; inspect alpha, images and gradients.
Exceptions and limits
Do not turn the exceptions into blanket permission to make disabled information unreadable.
Basis
WCAG 2.2: contrast minimum

COL-03 Boundaries and indicators remain visible

Proposed reviewer rule · not adopted · external requirement has its own source

Review the contrast of necessary control boundaries, state indicators and meaningful graphics.

Applies to
Interactive and graphical components
How to review
Apply SC 1.4.11 in context, including its 3:1 requirement and exceptions.
Exceptions and limits
Not every decorative border is necessary to identify a control.
Basis
WCAG 2.2: non-text contrast

PREF-01 Preferences are independent

Proposed reviewer rule · not adopted

Record colour scheme, forced colours, prefers-contrast and theme settings separately.

Applies to
All themes
How to review
Test individual preferences and useful combinations; retain unsupported values as unknown.
Exceptions and limits
A site setting may deliberately override a browser preference; document its precedence.
Basis
CSS Color Adjustment: forced colours

PREF-02 Distinguish simultaneous states

Proposed reviewer rule · not adopted

Keep selected, invalid, focused and disabled states distinguishable when they occur together, including forced colours.

Applies to
Forms, tabs, details and navigation
How to review
Review text, shape, boundaries and keyboard focus in each combined state.
Exceptions and limits
A double border in a local issue patch is not an accepted global Drupal design rule.
Basis
WCAG 2.2: use of colour; CSS Color Adjustment: forced colours; WCAG 2.2: focus not obscured minimum

PREF-03 Motion must have an alternative

Proposed reviewer rule · not adopted

When motion communicates progress or the next action, retain an understandable static cue under reduced motion.

Applies to
CSS and script-driven motion
How to review
Trigger the behaviour in both modes and review completion, orientation and feedback.
Exceptions and limits
Essential motion needs a documented rationale. SC 2.3.3 is AAA, not a blanket AA ban on animation.
Basis
WCAG 2.2: animation from interactions

PREF-04 Review residual transitions

Proposed reviewer rule · not adopted

Review remaining motion by property and purpose, not just duration or count.

Applies to
All components, including third-party UI
How to review
Separate declared transitions, observed animation and smooth scrolling. Trigger hover, focus, expand and validation states.
Exceptions and limits
A short colour fade is not automatically equivalent to spatial movement or an accessibility failure.
Basis
Proposed Lab contract; no external adoption claimed. · Evidence: motion-20261017

8. Components and page patterns

Review the same component family across pages, modules and recipes. Include default, focus, selected, expanded, invalid, disabled, loading and empty states where relevant. Changing the page count alone does not provide this state coverage.

TXT-01 Consistent interface language

Proposed reviewer rule · not adopted

Use sentence case for ordinary interface headings and labels; retain proper names. Keep help separate from labels.

Applies to
English interface strings
How to review
Review text in context and against the published UI wording guidance.
Exceptions and limits
Translation, proper nouns and established product names need language-aware review.
Basis
Drupal interface text; Drupal form elements

LAY-01 Layout preserves task access

Proposed reviewer rule · not adopted

Keep content and focused controls usable under narrow widths, text expansion and persistent navigation.

Applies to
Screen layout
How to review
Check overlap, clipping, wrapping, zoom and keyboard access, including AJAX states.
Exceptions and limits
Geometry intersections alone do not establish obscuration.
Basis
WCAG 2.2: focus not obscured minimum

CMP-01 Action hierarchy matches purpose

Proposed reviewer rule · not adopted

Use buttons for actions and links for navigation; select a primary action deliberately.

Applies to
Buttons, links and dropbuttons
How to review

Exceptions and limits
Wizard controls and component patterns need contextual review.
Basis
Drupal buttons

CMP-02 Grouping conveys relationships

Proposed reviewer rule · not adopted

Use semantic grouping for related fields and disclosure patterns for optional detail.

Applies to
Fieldsets, details and vertical tabs
How to review

Exceptions and limits
Do not convert older numerical limits or collapse recommendations into universal automated failures.
Basis

Proposed reviewer rule · not adopted

Applies to
Listings and multivalue widgets

9. Print is a first-class output

Define print intent for each page family. A content list, a configuration record, an article draft and a help page may preserve different context. Removing interactive chrome can be reasonable, but blanket selectors can also remove meaningful content.

Use scoped print CSS and review the resulting document. Reset persistent positioning where it conflicts with paper flow, preserve useful table headers, and keep headings with their content. These are proposed implementation directions, not a tested patch for Drupal.

PRN-01 Declare what printing preserves

Proposed reviewer rule · not adopted

For each page family, identify essential content, useful context and interactive chrome that may be omitted.

Applies to
Print output
How to review
Check inclusion, removal and restyling separately. Keep the reason for each omission.
Exceptions and limits
Do not hide every nav, aside, button or form element globally; some are part of the document.
Basis
Proposed Lab contract; no external adoption claimed. · Evidence: print-20261017

PRN-02 Paper layout must not cover content

Proposed reviewer rule · not adopted

Prevent navigation, sticky panels and editor sidebars from covering or clipping printed content.

Applies to
A4 and Letter output
How to review
Inspect paper-width layout and exported pages. Browser-viewport rectangles are supporting evidence only.
Exceptions and limits
An intentional repeated header is acceptable if it does not obscure content.
Basis
Proposed Lab contract; no external adoption claimed. · Evidence: print-20261017

PRN-03 Validate pagination and appearance

Proposed reviewer rule · not adopted

Review page breaks, repeated headers, blank trailing sheets and meaning with backgrounds disabled.

Applies to
Browser printing and PDF export
How to review
Inspect A4 and Letter, long tables, expanded detail and monochrome appearance.
Exceptions and limits
A PDF file existing, or matching page counts, does not establish quality or accessible PDF structure.
Basis
Proposed Lab contract; no external adoption claimed. · Evidence: print-20261017

Known collector gap: the current overlap heuristic measures the 1280px emulated print viewport. It reported zero intersections while paper-width PDFs visibly showed overlap. Treat those zeroes as inconclusive. Validate paper-size geometry and fragmentation before using the heuristic as a rule gate.

10. CKEditor and authored content

CKEditor has both interface styles and content styles. An editor toolbar need not look identical to a Drupal button, and an authored heading need not look like an administrative page title. Overrides should follow a recorded intent and remain scoped to the correct region.

EDT-01 Separate editor UI and content

Proposed reviewer rule · not adopted

Review editor controls, editable content and saved frontend output as separate styling contexts.

Applies to
CKEditor integrations
How to review
Record region, text format, editor version and owning stylesheet before overriding a difference.
Exceptions and limits
Editor chrome can legitimately differ from the admin theme; changes need component-level validation.
Basis
CKEditor 5 theme customization; CKEditor 5 content styles · Evidence: article-editor

EDT-02 Formatting retains meaning

Proposed reviewer rule · not adopted

Verify that allowed formatting produces the intended markup and survives saving and rendering.

Applies to
Rich-text workflows
How to review
Use explicit test content and editor actions; compare editor content with the saved frontend result.
Exceptions and limits
Text-format filtering and content-theme overrides can intentionally change the allowed output. Current captures did not test this.
Basis
CKEditor 5 content styles; HTML text-level semantics

The current Article capture contains 101 editor UI elements and three editable-content elements on each side. That establishes initial editor presence only. Add a known test node with text, headings, emphasis, links, lists and a table before testing edit/save/frontend consistency. Record its text format and the actual frontend theme. Use test content; never collect credentials or private production material.

11. Other themes, languages and recipes

Extend this reference through theme-specific profiles. Keep shared semantic expectations separate from typography, colour and layout choices. A recipe can change the available content types, fields and editor configuration without a theme change. Track those changes rather than treating the old fixture as universal.

I18N-01 Adapt without changing intent

Proposed reviewer rule · not adopted

Review translated text, direction and regional variants with the same component intent.

Applies to
Localised and conditional themes
How to review
Test language negotiation, logical directions, wrapping and state indicators in RTL and LTR.
Exceptions and limits
Different fonts, strings and dimensions are expected; compare roles and behaviour, not identical pixels.
Basis
Proposed Lab contract; no external adoption claimed.

13. Rules for AI reviewers and maintainers

  1. Read this document’s status and the target version before evaluating a page.
  2. Identify component, owner, theme and state. Preserve unknown values.
  3. Use a stable rule ID and cite its source or evidence. Separate observation from intended behaviour.
  4. Compare equivalent contexts. Do not turn a different theme, translated string or editor-content style into a defect merely because it differs.
  5. Report introduced, resolved, persistent and not-comparable findings separately. Do not subtract totals to infer matching findings.
  6. For bold or italics, explain the intended meaning and the component variant before suggesting markup or CSS changes.
  7. Propose the smallest change at the owning layer. Do not apply site-wide overrides to hide a component-level problem.
  8. Record evidence gaps and intentional exceptions. No automatic fix or conformance claim follows from this draft.

GOV-01 Exceptions are reviewable

Proposed reviewer rule · not adopted

Record intentional differences with rule ID, scope, owner, rationale, evidence and review condition.

Applies to
Modules, themes and recipes
How to review
Compare exceptions and baseline identities before classifying a new finding.
Exceptions and limits
Do not use a broad theme exception to suppress unrelated component or semantic failures.
Basis
Proposed Lab contract; no external adoption claimed.
