# Observability architecture

This document describes how optional execution tracing fits Drupal Core Lab's existing architecture. It is an
incremental extension: the existing environments, viewer, Playwright runs, axe-core, Lighthouse and Markdown reports remain
the system of record. The full set of observability documents is in [README.md](README.md).

## 1. Current environment architecture

Core Lab is issue-focused. It builds two disposable Drupal Core checkouts from one pinned (or current) revision:

```text
envs/core.git                 shared bare Git repository
envs/baseline-main/           Before: upstream revision
envs/issue-3619127-vanilla/   After:  same revision + declared patch stack
tools/compare/serve.mjs       side-by-side viewer and proxies
tools/playwright/             scripted real-input runs, axe, screenshots
reports/issues/<nid>/         the evidence that is kept
cloud/                        generated static GitHub Pages site
```

Observability settings are per environment (environment id, side, endpoint, capture flags) and are written into that
checkout's `sites/default/settings.php` by the CLI. They are deliberately not put in the repository-wide `lab.config.yml`:
a shared value cannot distinguish Before from After, and a mistake there would mix traces from the two sides. `lab.config.yml`
continues to hold only repository-wide settings.

Each checkout is a Git worktree and its own DDEV project (`ddev config --project-type=drupal12 --omit-containers=db`), so
Before and After have separate SQLite databases, files, sessions and caches. `tools/compare/setup.mjs` records the exact
commit and the content hash of every patch. `scripts/lab-env.mjs` starts and stops pairs and the viewer. The viewer reaches
each site through a same-origin proxy so the two admin sessions cannot collide (`tools/compare/README.md`).

The public site cannot run Drupal. `cloud/` is generated by `scripts/build-cloud.mjs`, committed, and published as static
files by `.github/workflows/pages.yml`.

## 2. Existing test execution flow

1. A variant in `tools/compare/variants.json` (or an issue's own `variants.json`) names the issue, the Before and After
   environment directories, the patch stack, the recipe, the pages, reproduction steps and checks.
2. `tools/compare/setup.mjs <slug>` fetches core, creates the worktrees, applies patches, installs Drupal, applies the
   recipe, and records the observed state (`env-state.mjs`, `patch-state.mjs`).
3. A Playwright evaluator under `tools/playwright/evaluate-<nid>.mjs` (or `walkthrough.mjs`) logs in with a one-time
   link, performs the scenario with real input, runs axe-core, records pages, AJAX commands, announcements, JavaScript
   errors and screenshots, and writes `results.json` plus `SUMMARY.md` to `reports/issues/<nid>/playwright/<stamp>/`.
4. The viewer can repeat the scenario interactively, with mirrored input, device widths, colour schemes, forced colours,
   onion and difference views, keyboard checks and live axe/Lighthouse.
5. `node scripts/coverage.mjs <nid>` turns runs into a tested/untested matrix; `scripts/run-readmes.mjs` generates run
   indexes; `scripts/index-issues.mjs` rebuilds the issue list.

The run record already contains the exact commits (`results.json.commits`), patch state (`patchState`), recipe/identity
(`identity`), browser/PHP/Drupal versions (`environment`, `site`), and a verdict with an explicit "unexpected" count.

## 3. Existing evidence collection

Evidence is kept in its native format, not translated:

| Evidence | Where | What it establishes |
|---|---|---|
| Playwright results and screenshots | `reports/issues/<nid>/playwright/<run>/` | What the browser did, under which browser/browser version, colour scheme and viewport |
| axe-core output | `results.json` and run summaries | Automated rule findings with the scanner's own rule id, impact, tags and nodes |
| Accessibility-tree / speech evidence | `tree-diff`, Guidepup and run summaries | Exposed semantics, announcements, and silent changes |
| Lighthouse and resource measurements | `reports/issues/<nid>/lighthouse/`, `resources/` | Page-load categories and serial resource benchmarks |
| Patches and revisions | `branches/`, `BRANCHES.md`, `results.json` | Exactly what was compared |
| Human review | `EVIDENCE.md`, `SUMMARY.md`, `ISSUE-COMMENT-DRAFT.md` | What a person confirmed, and what remains unknown |

The lab's rule is that a result without its revision and patch state is not evidence. Reports stay DRAFT until a person
reviews them.

## 4. Existing report structure

`reports/issues/<nid>/SUMMARY.md` is the entry point. It links `REPRODUCE.md`, `EVIDENCE.md`, `STATUS.md`,
`BRANCHES.md`, coverage, Playwright run folders, screen-reader evidence and comparison reports. Run folders contain a
generated `SUMMARY.md` and the raw artifacts. `reports/issues/README.md` is the index; `cloud/` presents the variants and
steps as a static guide.

There is no dashboard. Observability therefore adds a section to the existing run report and a tab to the existing viewer,
not a second reporting system.

## 5. Current before-and-after comparisons

Comparisons are already multi-dimensional:

- **Visual:** side-by-side, onion skin and difference views in the viewer.
- **Behavioural:** the variant's `checks` and the Playwright evaluator's verdict.
- **Accessibility:** axe counts/rules/nodes, accessibility-tree diffs, announcements.
- **Served output:** `tools/compare/diff.mjs` normalises both sites and reports differing HTML/CSS/JS.
- **Performance:** optional Lighthouse and serial resource measurements, with the caveat that shared machines are noisy.

A difference is presented as an observation. The existing reports state that a passing automated check is not WCAG
conformance, and that a verdict is a DRAFT until reviewed. The execution comparison keeps that rule.

## 6. Opportunities for trace integration

The useful question the current evidence cannot answer is: *which Drupal requests produced the page state the browser
saw, and what did Drupal do inside them?* Adding one trace id that both sides understand answers it without replacing any
existing artifact:

```text
Playwright action  ──►  HTTP request  ──►  Drupal route/controller  ──►  response
      │                    │                      │
      │                    │                      ├── database queries (count/time, no SQL)
      │                    │                      ├── cache-table activity (inferred)
      │                    │                      └── exceptions (class/count only)
      │                    │
      └── screenshot, axe finding, action id, request id, trace id
```

This correlates:

- an axe finding with the request that rendered the page it was found on;
- a visible change with the route/controller that produced it;
- a before/after difference in request count, server time, database work, cache activity or exceptions;
- a patch with an exact revision and an exact trace, for a later contributor to reproduce.

It does **not** prove causation. Instrumentation changes timing, cache state changes query counts, and a route/controller
can be chosen by configuration rather than by the patch. The manifest therefore records `observed` and `comparability`
separately from `correlation`, and the report says what was not established.

## 7. Dependencies and limitations

| Dependency | Status | Why it is acceptable |
|---|---|---|
| OpenTelemetry PHP SDK (`open-telemetry/sdk`, `open-telemetry/exporter-otlp`) | Already installed by Drupal core's dev dependencies at the pinned commit; Apache-2.0 | No new Composer requirement in a core checkout, and no proprietary SDK |
| W3C Trace Context | Recommendation since 2021 | Standard header (`traceparent`), not a lab-specific protocol |
| OpenTelemetry Collector contrib | Pinned container `0.165.0`, optional | Local, open source, no hosted account |
| Drupal `core_lab_observability` module | Lab-owned, small, disabled by default | Thin Drupal integration; no upstream module is installable on this core (see [INTEROPERABILITY.md](INTEROPERABILITY.md)) |
| Playwright | Existing dependency | Trace context is injected explicitly; no Playwright-OTel package is required |
| Jaeger/Tempo/Grafana | Not required | OTLP output can be sent to any of them later; the lab reads its own sanitised summaries |

Known limits:

- **Page cache.** Drupal's page cache can return a response before the kernel request event, so that request may have no
  route/database trace. Authenticated admin pages (the usual Core Lab scenario) are not page-cached; the limitation is
  recorded in each manifest.
- **Timing.** The server span starts at the kernel request event, after Drupal bootstrap, and ends at terminate. It is not
  total PHP time. Database logging and OTLP export add overhead.
- **Database detail.** Query count and statement time are recorded; SQL text and arguments are not. Cache activity is
  inferred from queries against cache tables, not from hit/miss counters.
- **Component provenance.** Form API elements, render arrays, Twig templates and libraries are not attributed by this
  pilot. See [INTEROPERABILITY.md](INTEROPERABILITY.md).
- **Cloud.** DDEV Coder workspaces use Docker inside the workspace, so the collector runs there too; the viewer's
  existing origins and port bindings are unchanged. Networking is documented in [SETUP.md](SETUP.md).
- **Static site.** `cloud/` contains only a sanitised summary generated during collection. It never contacts a collector.

## 8. Proposed implementation boundaries

Within this pilot:

- Optional module, optional collector, no change to a core checkout's `composer.json`.
- One trace context per browser side per run; one request catalogue per side; one manifest per run.
- Server spans: request, controller/render approximation, aggregate database/cache attributes and exception counts.
- Evidence: a versioned JSON manifest, a Markdown section in the existing run report, a sanitised static summary, and a
  viewer tab that is hidden when no evidence exists.
- A single comparison is not hard-coded to two environments: `environments[]` carries role/id/revision/patches, and every
  request and trace names its `environment_id`.
- Raw artifacts stay local; only small, sanitised summaries are committed.

Out of scope: replay, a hosted observability service, arbitrary trace queries, AI attribution, a Rosetta implementation,
MCP, and per-query spans. Those are recorded as deferred in [INTEROPERABILITY.md](INTEROPERABILITY.md).
