# Drupal Core Accessibility: Resolve Issue #2942404

## Objective
Investigate and resolve the remaining accessibility problems with Drupal's system messages, focusing on reliable screen reader announcements, correct semantic structure, and consistent behavior across full-page reloads, AJAX, and BigPipe.

**Primary issue:** [https://www.drupal.org/project/drupal/issues/2942404](https://www.drupal.org/project/drupal/issues/2942404)

**Related issue:** [https://www.drupal.org/project/drupal/issues/3587678](https://www.drupal.org/project/drupal/issues/3587678)

**Target:** Drupal 12, using the current Drupal core `main` branch.

**Priority:** Deliver the smallest standards-compliant fix supported by reproducible evidence, with appropriate regression tests.

Do not assume that the original problem is still present. First establish which changes have already been committed and whether additional code changes are actually needed.

## Background
Drupal displays system messages to communicate successful actions, errors, warnings, and other status information.

Historically, Drupal incorrectly used `role="contentinfo"` for some system messages. This role represents document-level information, generally associated with a page footer, rather than notifications.

The related issue #3587678 reportedly corrected this behavior in August 2026, replacing inappropriate landmarks with more suitable semantics, including `role="status"` and `role="alert"`.

However, related discussions suggest that some accessibility problems may remain:

1. Messages following a full-page reload may not be announced automatically.
2. AJAX-inserted messages may be announced differently from server-rendered messages.
3. BigPipe may introduce additional timing or announcement differences.
4. Drupal's JavaScript announcement mechanism may duplicate announcements already generated by live regions.
5. System messages may not be consistently discoverable through headings and keyboard or assistive-technology navigation.
6. Multiple messages may produce confusing or repetitive announcements.
7. Theme-specific templates may introduce inconsistent markup.
These are investigation targets, not confirmed defects in the current code.

The objective is to establish actual behavior before proposing a correction.

## Phase 2: Establish accessibility requirements
Use the relevant standards and guidance.

### WCAG 2.2
Evaluate applicable requirements, particularly:

- **1.3.1 Info and Relationships (Level A):** Appropriate programmatic semantics and structure.
- **2.4.3 Focus Order (Level A):** Predictable keyboard navigation when changes affect focus.
- **4.1.3 Status Messages (Level AA):** Programmatic determination of status messages that do not receive focus.
Also consider other success criteria where the specific behavior provides evidence that they apply.

Reference:

- [https://www.w3.org/TR/WCAG22/](https://www.w3.org/TR/WCAG22/)
- [https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)

### WAI-ARIA
Review:

- `role="status"`
- `role="alert"`
- `aria-live`
- `aria-atomic`
- `aria-relevant`
- Live-region behavior and timing.
Reference:

[https://www.w3.org/TR/wai-aria-1.2/](https://www.w3.org/TR/wai-aria-1.2/)

Do not add ARIA attributes indiscriminately.

Native HTML semantics and existing accessible behavior should be preserved wherever possible.

### Important distinction: Full-page navigation versus dynamic updates
A live region that is present when a page loads does not necessarily generate the same announcement as a live region updated after loading.

Do not assume this is a WCAG failure without examining the interaction and applicable success criteria.

For a full-page reload, users must be able to discover and understand the message. Automatic announcement of every message is not inherently required.

For dynamic changes that do not move focus, evaluate whether the user is adequately informed and whether WCAG 4.1.3 applies.

Avoid attempting to solve full-page announcements by adding redundant live regions.

## Phase 3: Build reproducible test scenarios
Use an existing Drupal testing environment wherever possible.

Prefer Drupal core's established testing infrastructure. DDEV may be used locally if already configured.

### Scenario A: Full-page reload

1. Create a basic content item.
2. Save it.
3. Observe the resulting confirmation message.
4. Repeat with an error-generating form.
5. Repeat with a warning message.
Record:

- Rendered HTML.
- Message position in the document.
- Accessible structure.
- Heading relationships.
- Keyboard focus after navigation.
- Whether the message is discoverable with assistive technology.

### Scenario B: AJAX insertion
Use an existing core AJAX form or component to trigger a message without reloading the page.

Test successful and unsuccessful operations.

Observe:

- Whether a message is inserted.
- Whether an existing message is replaced.
- Whether focus changes.
- Whether the live region announces the change.
- Whether `Drupal.announce()` is also invoked.
- Whether the message is announced more than once.

### Scenario C: BigPipe
Run equivalent tests with BigPipe enabled and disabled.

Investigate whether streaming and rendering timing affect message announcement or discoverability.

Only treat differences as defects where they negatively affect accessibility.

### Scenario D: Multiple messages
Generate multiple status, warning, and error messages.

Verify:

- All messages remain visible.
- All messages remain programmatically available.
- Messages are presented in a comprehensible order.
- Live announcements are not needlessly repeated.
- Important errors are not obscured by lower-priority notifications.
- Messages do not disappear before users can read them.

### Scenario E: Theme consistency
Test the currently supported core frontend and administration themes, including Olivero and the administration theme used by the target Drupal version.

Confirm that semantic differences are intentional.

### Scenario F: Progressive enhancement
Test with JavaScript disabled.

Confirm that server-rendered messages remain available and meaningful without client-side announcement logic.

## Phase 5: Determine the smallest viable fix
Use the Phase 1 through 4 findings to select an implementation.

### Case A: The issue is already resolved
If the original defect has been fixed and no remaining reproducible accessibility problem is demonstrated:

- Do not change Drupal code.
- Document the evidence.
- Identify the commit or related issue that resolved the problem.
- Recommend closing #2942404, with a rationale based on its current status and issue history.
- Create separate follow-up recommendations only for independently verified defects.
Avoid creating unnecessary patches.

### Case B: Duplicate dynamic announcements
If testing confirms messages are spoken more than once:

- Trace whether the duplicate is caused by both `Drupal.announce()` and live-region behavior.
- Identify which mechanism should own the announcement for that interaction.
- Preserve appropriate message semantics.
- Remove redundant announcement behavior only where the result is verified.
- Ensure the correction does not suppress other important announcements.
Add a regression test for the specific execution path.

### Case C: Messages are not announced when dynamically inserted
If an applicable dynamic status message is not announced:

- Investigate live-region presence and insertion timing.
- Examine the interaction between `Drupal.Message` and `Drupal.announce()`.
- Correct the smallest responsible component.
- Avoid introducing global focus changes.
- Verify behavior for multiple sequential messages.

### Case D: Messages are difficult to find after navigation
If messages are present but difficult to discover following a full-page reload:

- Examine their location in document order.
- Review existing heading semantics.
- Evaluate how the page title and messages are presented.
- Consider whether existing markup can be improved without changing interaction behavior.
- Avoid automatically focusing every message.
Keep navigation and discoverability separate from live announcements.

### Case E: Theme-specific defects
If a problem occurs only in a theme override:

- Identify the responsible template or behavior.
- Fix it at the appropriate layer.
- Avoid unnecessary changes to shared message APIs.
- Preserve compatibility with contributed themes as far as practical.

## Phase 6: Implement the correction
Only proceed after identifying a reproducible defect.

Requirements:

1. Keep the patch small and focused.
2. Follow Drupal core coding standards.
3. Preserve existing public APIs unless changes are demonstrably required.
4. Avoid adding dependencies.
5. Preserve translations and message contents.
6. Preserve behavior without JavaScript.
7. Do not introduce unnecessary focus changes.
8. Do not introduce duplicate ARIA attributes or landmarks.
9. Reuse existing Drupal conventions.
10. Follow current Drupal core test patterns.
Avoid the following unless the evidence establishes a need:

- Replacing the entire message system.
- Converting standard form submissions to AJAX.
- Introducing htmx.
- Adding a new JavaScript framework.
- Removing useful headings.
- Duplicating live regions.
- Automatically shifting focus after every message.
- Creating a new announcement manager.
- Refactoring unrelated accessibility code.
Prefer correcting an existing mechanism over creating a parallel one.
