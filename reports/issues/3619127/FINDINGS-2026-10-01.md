# Findings while evaluating #3619127 (2026-10-01)

## 1. The patch does what the issue asks
Real mouse click and keyboard-only (focus the link, press Enter), at 480 px: on upstream `main` the sidebar
does not open and the field is not focused or in view; with the MR plus patches 0 and 1 the sidebar opens, the
URL alias field receives focus and is in the viewport. Saved sidebar preference unchanged, axe 0 violations on
both sides before and after, no JavaScript errors.

## 2. Not caused by the patch: the inline error is not announced with the field
On upstream `main` (baseline) the URL alias field has `aria-invalid="true"` but `aria-describedby` references only the
help text (`edit-path-0-alias--description`). The visible error "The alias path has to start with a slash." is in a
`.form-item__error-message` element with no `id`, no role and no association. The Guidepup virtual screen reader
announces "textbox, URL alias, no-slash, Specify an alternative path by which this data can be accessed ..., invalid"
on both sides: the user hears that the field is invalid but not why. WCAG 3.3.1 (Error Identification), 1.3.1, 4.1.3
are the relevant criteria to check. Same theme as #3083103 (programmatically associate the error); check that issue
before filing anything new. Confirmed with the synthetic Guidepup virtual screen reader and by reading the DOM. A real VoiceOver/NVDA check is deferred (decision 2026-10-01: synthetic is enough for now).

## 3. Method lessons
- A script-generated click does not trigger the form's focus behaviour; use trusted input for the final step.
- Only one frame can hold focus, so record focus when it happens instead of reading it afterwards.
- An upstream test (`FormErrorHandlerCKEditor5Test::testFragmentLink`) is flaky on pristine `main` (2 failures in 6 runs).

## 4. Dark mode exposes an existing contrast failure (found by the browser and colour-mode matrix)
In **dark mode**, in both Chromium and WebKit, axe reports `color-contrast` failures that light mode does not (light: 0 on both
sides). Before: 2 (the Title field's label and error text). After: 4, because the invalid URL alias field is now visible once the
sidebar opens. The failing colour is the form-error text `#ce6060`: on `#2a2a2d` it is **3.72:1** (Title) and on `#1b1b1d` it is
**4.47:1** (URL alias label and error message), against the 4.5:1 needed for WCAG 1.4.3.

This is not introduced by the patch. It is the defect tracked in **#3625458** ("form error text dark mode contrast", `#ce6060` to
`#d67a7a`, MR !17225, RTBC), which the patch makes visible in one more place by doing its job. Expect the two extra failures to
disappear once #3625458 lands. If they do not, the sidebar's dark surface needs its own check. To confirm, run
`node tools/playwright/walkthrough.mjs 3619127-pinned --browser=chromium --scheme=dark` against a core with #3625458 applied.
(Evidence: `playwright/*-chromium-dark-*/` and `*-webkit-dark-*/`; the elements and ratios came from an axe run listing each node.)
