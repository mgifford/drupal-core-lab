A throwaway copy of `baseline-main` with the lab-owned `upload_dirs: [.ddev/tmp, core/node_modules]` was started while the
active pair stayed up. After a quiet period (the first samples showed initial hashing spikes of 15-41%):

The web-CPU comparison is noisy because host load and `docker stats` sampling affect it; the Mutagen agent figure is the stable
one. The probe's login page returned 200. It was stopped, deleted and removed; the active pair still returned 200 afterwards.

The probe's first `ddev start` reproduced the known router failure (`ddev-router failed to become ready`); `docker restart
ddev-router` restored all active routes. A retry started the probe but warned `Router count mismatch: 22 loaded, 28 expected`.
This remains a multi-pair start risk, not a safe routine.

## Changed in this stage

1. **Docker accounting** ([tools/resource/adapters/docker.mjs](../../tools/resource/adapters/docker.mjs))
   - Selects containers by DDEV labels (`com.ddev.site-name`) plus the shared `ddev-router`/`ddev-ssh-agent`, not by a
     `ddev-*-web` name guess. Unrelated projects (Primero) are excluded.
   - Records roles: web, chrome, db, otel-collector, router, ssh-agent, viewer; environment and issue where known.
   - CPU is sampled as `CPUPerc` with derived CPU-seconds; disk/network are interval deltas from cumulative counters, with
     cumulative values kept in `private`; labels say sampled/derived. No exact CPU claim.
   - A two-sample run collected **9 containers**: 2 web, 2 Chrome, 2 OTEL, 1 viewer, router, SSH agent.
   - Tests: [tests/lab/resource-docker.test.mjs](../../tests/lab/resource-docker.test.mjs).

2. **`node scripts/lab-env.mjs resources [--json]`**
   - Read-only: host load/memory, Docker VM CPU/memory/disk, per-environment state/core/variants, web/Chrome/OTEL memory,
     Mutagen status/file count/size, total lab memory/CPU, shared services, running wrapped operations, declared tasks.
   - Activity is explicitly **unknown** without a task lease; it never says idle and never stops anything.
   - Warns when `core/node_modules` is still synced in an existing environment.
   - Verified live on the active pair.

3. **Lab-owned DDEV override for new environments**
   - `setup.mjs` writes `.ddev/config.lab.yaml` with `upload_dirs: [.ddev/tmp, core/node_modules]`.
   - Validated without starting a new pair: a copy's `ddev utility configyaml` showed `core/node_modules` in the effective
     `upload_dirs` (DDEV merges the arrays; `.ddev/tmp` appeared twice, harmless). The copy was deleted.
   - Existing environments keep their current session; applying it needs a deliberate restart/reset.
   - Tests: [tests/lab/ddev-config.test.mjs](../../tests/lab/ddev-config.test.mjs).

4. **Infrastructure Efficiency report and dashboard section**
   - `aggregate` now emits `infrastructure`: sampled container roles, container count, samples, derived CPU-seconds and peak
     memory, with older role-less samples counted separately (`unclassified_samples`).
   - `reports/resources/SUMMARY.md` has an "Infrastructure services (sampled)" table; `tools/resource/dashboard.html` has an
     accessible "Infrastructure efficiency (sampled)" section with a table, not a live view.
   - Regenerated with 27 role-labelled samples across 9 containers; 8 older samples stay in "By tool" only.
   - `resource-dashboard.mjs`: 6/6 contexts, 24 tables, 299 rows, 0 axe violations, 0 page errors. This is automated
evidence only: the new Infrastructure efficiency section has **not** had a manual keyboard or screen-reader pass.

5. **Chrome lifecycle command**
   - `node scripts/lab-env.mjs chrome <slug> stop|start` stops/starts only the pair's Chrome containers; Drupal stays up.
   - `start` waits for the container and Selenium `/status` before reporting success; `stop` waits for the container to stop.
   - Tested stop/start on the active pair; both containers returned with Selenium ready. Browser tests still need an explicit
     start (the command does not auto-start Chrome).
6. **Local environment leases and lifecycle protection**
   - `tools/compare/leases.mjs` stores expiring, host-aware leases under `.lab-cache/lab-env-leases.json`; they are runtime
     coordination, not task records, and may name an existing `resource-task` id.
   - `lab-env claim <slug> [--task=id] [--operation=name] [--minutes=60]`, `release <slug>` and `leases` are added.
   - `stop`, `reset`, `delete`, `retire` and `chrome stop` refuse while a lease is active; `--force` is the explicit override.
   - TTL-only leases (the one-shot CLI) stay active until released or expired; PID leases also require the process to be alive.
     A missing/expired/stale lease is reported as **unknown**, never idle.
   - Verified: claim `3619127-pinned`, `stop` refused without stopping anything, `resources` showed both environments
     `active (review, issue-3619127)`, then release removed it.
   - Tests: [tests/lab/leases.test.mjs](../../tests/lab/leases.test.mjs).

7. **Observe-only capacity advisor**
   - `tools/compare/scheduler.mjs` counts active `resource-run` operations and active heavy leases, deduplicated by PID, against
     the existing `max_concurrent_cpu_jobs` budget.
   - `lab-env capacity [--kind=test] [--json]` reports allow/record/warn/refuse advice plus Docker memory pressure; it never
     starts, stops or refuses anything itself.
   - Default mode is observe. Enforcement would require a caller to check the decision before starting; no queue is enforced.
   - Live check: `allow` for `kind=test`, 0/2 heavy work, 17.2% Docker memory, 1.36 GiB lab containers.
   - Tests: [tests/lab/scheduler.test.mjs](../../tests/lab/scheduler.test.mjs).

8. **FunctionalJavascript test guard**
   - `scripts/try-tests.mjs` detects FunctionalJavascript/WebDriverTestBase tests and starts the pair's Chrome containers before
     PHPUnit, waiting for Selenium on port 4444.
   - A missing container or an unresponsive Selenium fails with a clear message and exit 3 before the test is called a failure.
   - Chrome is left running after the tests; Nightwatch still needs `lab-env chrome <slug> start`.
   - Tests: [tests/lab/browser-tests.test.mjs](../../tests/lab/browser-tests.test.mjs) for detection and container naming.
   - A live `JavascriptErrorsTest` run passed 2/2 on both sides and exercised the guard, but the run's explicit `ddev mutagen sync`
     then pulled a stale `default_admin` theme from the baseline container into Before. The run correctly reported
     `before tracked files changed` as PROBLEM.
   - Repaired: restored tracked files, removed only stale untracked theme assets, copied the clean host theme into the baseline
     container, flushed, and verified Before has 0 tracked changes; both sites and the viewer return 200.
   - `try-tests` no longer calls `ddev mutagen sync`; it waits for the copied files to reach the container, compares tracked and
     untracked files for new changes, but does not treat a pre-existing untracked fixture as a dirty baseline.
   - Rerun after the fix: Chrome ready on both sides, `JavascriptErrorsTest` 2/2 passed on Before and After, Result: nothing to
     flag, Before tracked changes 0. The guard path is verified.
9. **Mutagen snapshots as resource events**
   - `tools/resource/adapters/mutagen.mjs` runs the read-only `ddev mutagen status -l` for each running project and records
     files, declared content bytes, session count and state. It never flushes, resets or starts anything.
   - `measurements.mutagen` is optional in the schema; existing events still validate. `publicEvent` exposes only aggregate
     snapshot data; project paths and names stay private.
   - Latest snapshots: baseline 67,793 files / 438.7 MiB, issue 67,761 / 438.7 MiB, viewer 53 / 108.4 KiB. The viewer is
     labelled separately, not folded into the baseline.
   - `reports/resources/SUMMARY.md` and the dashboard have a Mutagen snapshots table. `collect --source=mutagen` is wired.
   - Tests: [tests/lab/resource-mutagen.test.mjs](../../tests/lab/resource-mutagen.test.mjs); parser fixture includes the
     `directories` line that the first implementation missed.
